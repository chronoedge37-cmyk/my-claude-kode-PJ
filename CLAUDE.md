# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Static site for a LINE Official Account fortune-telling business (五行庵 宗玄 / "五行タロット鑑定" — Five Elements × Tarot readings). No build system, no package manager, no backend/server — three self-contained HTML files, each with inline `<style>` and `<script>`, deployed as-is to **GitHub Pages** (Settings → Pages, "Deploy from branch", `main`, root). The site previously ran on Netlify (one-time "Netlify Drop", never linked to this repo) — that deployment is abandoned; `_redirects` is a leftover Netlify-only file with no effect on GitHub Pages.

There are no build, lint, or test commands — there is no `package.json` and nothing to compile. Verify changes by opening the HTML file directly in a browser (or the deployed GitHub Pages URL) and exercising the relevant flow manually.

`index.html` is a minimal `<meta http-equiv="refresh">` redirect to `intro-landing.html`, needed because GitHub Pages serves whatever is at the repo root and this project's real entry point is `intro-landing.html`.

## Pages and user flow

- `intro-landing.html` — entry page. Hero has a circular portrait slot (`assets/portrait/sougen.png`, a character illustration of 宗玄) ringed by a CSS-only rotating/breathing light-ray effect (`.rays`/`.ray`, generated in the inline `<script>`); if the portrait image is missing, `onerror="this.remove()"` leaves just the empty ring + rays rather than a broken-image icon — there is deliberately no filled placeholder graphic anymore. Links to `muryo-soudan.html`.
- `muryo-soudan.html` — free consultation / self-service diagnosis. Customer enters birth date (+ optional time) and gender; a client-side 四柱推命 (Four Pillars / bazi) engine computes and renders the chart entirely in the browser, including a dominant-element read (`maxI` in `runDiagnosis()`). The result panel shows an amulet image at `assets/amulets/{wood,fire,earth,metal,water}.png` chosen by that dominant element (same graceful `onerror` fallback as the portrait — these 5 files do not exist in the repo yet). The CTA button's `href` is built dynamically in `runDiagnosis()`: it points to `260805.html?mode=customer&pf=<encoded birth data>`, base64-encoding the customer's Y/M/D/H/Min/gender so the paid form can prefill them.
- `260805.html` — the paid-reading intake form **and** the practitioner's working page, in one file. Behavior is selected at runtime by a `?mode=` query param, dispatched at the bottom of the `<script>`:
  - `?mode=customer` (default) — customer form. `applyPrefill()` reads the `pf` URL param (if present, from the muryo-soudan.html CTA) and pre-fills/selects the birth-date and gender fields so the customer doesn't re-enter them. On submit (`submitCustomer()`), the data is base64-encoded into a URL (`enc()`/`dec()` helpers) that becomes the practitioner's `?mode=reading&d=...` link. `enc()`/`dec()` operate on raw UTF-8 bytes (via `TextEncoder`/`TextDecoder`), not `encodeURIComponent`-then-`btoa` — the latter blows up every Japanese character to ~9 ASCII chars before base64, which was making the LINE share link long enough to silently fail (see below); `dec()` still falls back to the old scheme so already-issued links keep working. Any base64 payload placed into a URL query string (the `d=` and `pf=` params) must be wrapped in `encodeURIComponent()` — base64's own `+`/`/`/`=` characters are otherwise corrupted (`+` in particular gets read back as a space) once `URLSearchParams.get()` parses them out. Clicking submit **automatically opens the LINE app to the recipient-picker with the message pre-filled** via `window.open(lineUrl, '_blank', 'noopener')`, called synchronously inside the click handler — no separate button needs to be pressed for this step. The correct LINE deep link format is `https://line.me/R/msg/text/?<encoded text>`; an earlier version used `https://line.me/R/share?text=...`, which is not a valid LINE endpoint and just opens the LINE app's own home screen instead of the send screen. The completion screen still shows a **"①LINEの送信画面が開かない場合"** fallback link (`#lineSendBtn`) for when a browser blocks the auto-opened window, plus **②a Stripe payment link** (with `client_reference_id=<name>` appended so the payment can be matched to the submission without asking for the name again). `sendEmailNotify()` (EmailJS) also fires in the background as a bonus/backup channel — see the EmailJS note below. The LINE message body truncates long free-text answers (始めたいこと/希望期間) to keep the share link comfortably short; the full text is never lost — it's always in the `d=` payload the reading link decodes.
  - `?mode=reading&d=<encoded>` — practitioner-only view. Decodes the payload, re-runs the same bazi engine plus 大運 (dayun/decade luck cycles), and provides textareas for the practitioner's commentary: ① 四柱推命, ② タロット, ③ 推奨日 第1候補(with a hint to skip boilerplate openers and write definitively — this is paid content), ④ 第2/3候補, ⑤ 動いてはいけない日 (hint explicitly bans wishy-washy phrasing like 「必要であれば」), ⑥ 総合アドバイス (hint requires tying the conclusion to this customer's 日主/命式/timeframe/request specifically, not generic advice). "報告書を生成する" (`buildReport()`) assembles everything into a plain-text report block for copy/paste, using `★`/`●`/`⚠️` markers to visually distinguish the top-pick day from the alternates and the avoid-day (plain text can't carry color), plus bracketed placeholders (`[🖼 ...]`, `[📷 ...]`) marking where the practitioner should attach the amulet image / tarot-spread photo when sending via LINE.
  - `?mode=setup` — stores EmailJS credentials (public key, service ID, template ID, notification email) in `localStorage` under `ej_cfg`. **This config is scoped per browser origin** — it does not carry over across domain migrations (e.g. the old Netlify domain to the current GitHub Pages domain) or between devices/browsers, so it silently stops working after any such change until re-entered. This is why EmailJS is treated as a bonus channel, not the primary one.

## Architecture notes

- **The bazi/four-pillars calculation engine is duplicated verbatim in `muryo-soudan.html` and `260805.html`** (solar longitude `sl()`, jieqi solar-term root-finding `flj()`, ganzhi conversion, `bazi()`, `tally()`, five-element weighting, etc.). There is no shared JS module — because there's no build step to share code between static pages, any fix or change to this engine must be applied in both files or they will silently diverge. `260805.html` additionally has the `dayun()` (大運) function that `muryo-soudan.html` doesn't need.
- All customer PII (name, birth date/time, gender, request, timeframe) flows only through the browser: form → base64(JSON) in a URL query param → LINE share text / EmailJS template params. Nothing is persisted server-side; `localStorage` on the practitioner's own device is the only persistence (EmailJS config only), and it does not sync across origins or devices (see the `?mode=setup` note above).
- **LINE share is the only guaranteed delivery channel from customer to practitioner.** An earlier iteration made EmailJS the sole automatic channel and hid LINE as a small "in case it fails" link; that silently broke the customer-to-practitioner flow entirely (nothing reached the practitioner, with no visible failure on either side) once the EmailJS `localStorage` config stopped applying after the Netlify→GitHub Pages domain change. LINE share requires no configuration and cannot silently fail the same way, so it must stay a required step — treat any future change here with that failure mode in mind. It no longer needs a second manual tap on our page though: `submitCustomer()` opens the LINE share screen automatically (`window.open`) in the same click as the main submit button, so from the customer's perspective there is effectively one button, matching how the original pre-outage version behaved. A browser can never be made to silently deliver into another native app with zero taps — the customer still has to tap "send" inside LINE itself once it opens; that final tap is a platform-level requirement, not something this codebase can remove.
- External dependencies are all CDN-loaded, no bundler: Google Fonts (Cinzel, Shippori Mincho B1, Shippori Antique B1, and Yuji Syuku on `intro-landing.html` only) on all three pages, and `@emailjs/browser` (jsdelivr CDN) on `260805.html` only.
- Visual language is shared but not code-shared across the three files: dark ink background, gold/lavender palette, "flowing star" canvas-free CSS animation. Each page defines its own copy of these styles.
- `assets/portrait/sougen.png` and `assets/amulets/{wood,fire,earth,metal,water}.png` are referenced by the HTML but treated as optional: every `<img>` for them has `onerror` handling so a missing file degrades gracefully (no broken-image icon) instead of breaking the page. As of this writing only `assets/portrait/sougen.png` exists; the 5 amulet images do not.
