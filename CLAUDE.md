# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Static site for a LINE Official Account fortune-telling business (五行庵 宗玄 / "五行タロット鑑定" — Five Elements × Tarot readings). No build system, no package manager, no backend/server — three self-contained HTML files, each with inline `<style>` and `<script>`, deployed as-is to **GitHub Pages** (Settings → Pages, "Deploy from branch", `main`, root). The site previously ran on Netlify (one-time "Netlify Drop", never linked to this repo) — that deployment is abandoned; `_redirects` is a leftover Netlify-only file with no effect on GitHub Pages.

There are no build, lint, or test commands — there is no `package.json` and nothing to compile. Verify changes by opening the HTML file directly in a browser (or the deployed GitHub Pages URL) and exercising the relevant flow manually.

`index.html` is a minimal `<meta http-equiv="refresh">` redirect to `intro-landing.html`, needed because GitHub Pages serves whatever is at the repo root and this project's real entry point is `intro-landing.html`.

## Pages and user flow

- `intro-landing.html` — entry page. Hero has a circular portrait slot (`assets/portrait/sougen.png`, a character illustration of 宗玄) ringed by a CSS-only rotating/breathing light-ray effect (`.rays`/`.ray`, generated in the inline `<script>`); if the portrait image is missing, `onerror="this.remove()"` leaves just the empty ring + rays rather than a broken-image icon — there is deliberately no filled placeholder graphic anymore. Links to `muryo-soudan.html`.
- `muryo-soudan.html` — free consultation / self-service diagnosis. Customer enters birth date (+ optional time) and gender; a client-side 四柱推命 (Four Pillars / bazi) engine computes and renders the chart entirely in the browser, including a dominant-element read (`maxI` in `runDiagnosis()`). The result panel shows an amulet image at `assets/amulets/{wood,fire,earth,metal,water}.png` chosen by that dominant element (same graceful `onerror` fallback as the portrait). The CTA button's `href` is built dynamically in `runDiagnosis()`: it points to `260805.html?mode=customer&pf=<encoded birth data>`, base64-encoding the customer's Y/M/D/H/Min/gender so the paid form can prefill them. **An optional `#f_nickname` field** (explicitly captioned "🔒 お名前・ご連絡先は不要です") lets `runDiagnosis()` personalize the result heading/greeting ("〇〇さんの命式" instead of the generic date-based title) without asking for anything more identifying than a birth date + a self-chosen nickname — this is the free/acquisition-funnel step, so it deliberately stays the most PII-minimal page in the site (contrast with the paid form's `#c_name`, which is required for Stripe's `client_reference_id` matching). **🎙️ voice input and 🔊 voice output** (both free, browser-native Web Speech API — see the Architecture notes entry below) let the customer speak their nickname and birth date instead of typing (`startVoiceNickname()`/`startVoiceDate()`, the latter regexing a spoken date like 「1990年5月20日」into the existing Y/M/D `<select>`s) and have the result read aloud (`toggleSpeak()`, reading a plain-text mirror of `#r_comment` kept in a hidden `#r_speakText`) — pitched directly as an accessibility/convenience feature ("障害が有っても言葉で占える"), not a gimmick; both mic and speaker buttons self-hide via feature detection where the browser lacks support (LINE's in-app browser, some Safari/Android builds), per this project's existing graceful-degradation rule.
- `260805.html` — the paid-reading intake form **and** the practitioner's working page, in one file. Behavior is selected at runtime by a `?mode=` query param, dispatched at the bottom of the `<script>`:
  - `?mode=customer` (default) — customer form: name, birth date/time, gender, **①「始めたいこと」(now a `<textarea>`, encouraged to include background/context, not just a one-line label)**, ②希望期間, and **③「今の状況や気になっていること」(`c_detail`, optional free-text)** added specifically so the practitioner has enough real material to write a personalized ⑥総合アドバイス instead of only the short example-length answers a single-line input invited. `applyPrefill()` reads the `pf` URL param (if present, from the muryo-soudan.html CTA) and pre-fills/selects the birth-date and gender fields so the customer doesn't re-enter them.
    **①「始めたいこと」と②希望期間 are both backed by a `<select>` first, to minimize typing.** `#c_action_preset` (options from the `ACTION_PRESETS` map: 転職・キャリアチェンジ / 起業・独立 / 恋愛・結婚 / 引っ越し・住み替え / 資格取得・受験 / 大きな買い物・契約 / その他) writes a one-line starter sentence into `#c_action` on `change`, but only if the textarea is still empty — it never overwrites something the customer already typed, so it's purely a typing-reduction convenience, not a constraint on what they can say. `#c_period_preset` replaces what used to be a free-text `#c_period` input entirely: its options are `1ヶ月以内` / `3ヶ月以内` / `半年以内` / a computed `<currentYear>年中` / `<currentYear+1>年中` (labelled "今年中"/"来年中" but the *value* is always the literal unambiguous year string, computed fresh from `new Date().getFullYear()` in `initForm()` so it never goes stale) / `特に期限はない` / `日付や年度を指定する(自由入力)` (value `__custom__`, which reveals `#c_period_custom` for anything the presets don't cover). This exists specifically because a free-text answer like "2027年" is genuinely ambiguous — "by 2027" vs "starting in 2027" are both natural readings, and when Claude later writes the actual day recommendations from this data (see below), guessing wrong means picking dates in the wrong year entirely. The preset values are unambiguous by construction, so this ambiguity cannot recur for any future submission; `submitCustomer()` reads `period` as `periodPresetVal==='__custom__' ? c_period_custom.value.trim() : periodPresetVal`. On submit (`submitCustomer()`), the data (including `detail`) is base64-encoded into a URL (`enc()`/`dec()` helpers) that becomes the practitioner's `?mode=reading&d=...` link. `enc()`/`dec()` operate on raw UTF-8 bytes (via `TextEncoder`/`TextDecoder`), not `encodeURIComponent`-then-`btoa` — the latter blows up every Japanese character to ~9 ASCII chars before base64, which was making the LINE share link long enough to risk failing (see below); `dec()` still falls back to the old scheme so already-issued links keep working. Any base64 payload placed into a URL query string (the `d=` and `pf=` params) must be wrapped in `encodeURIComponent()` — base64's own `+`/`/`/`=` characters are otherwise corrupted (`+` in particular gets read back as a space) once `URLSearchParams.get()` parses them out. **`#c_action` and `#c_detail` each have a 🎙️「声で入力する」button** (`startVoiceDictation(targetId, btnId)`, same free Web Speech API as `muryo-soudan.html` — see the Architecture notes entry) that appends the recognized speech to whatever's already typed, for the two fields most likely to be long and tiring to type on a phone; self-hides when unsupported.

    **Delivery is honest about what actually happened, not optimistic.** `submitCustomer()` fires `sendEmailNotify()` (EmailJS) and now *awaits its outcome* to decide what the completion screen tells the customer: on success, `#notifyStatus` shows "✓ 鑑定師のメールに自動で届きました" and the LINE step is relabeled "①LINEでも送る(任意)"; on failure/no-config, it shows a warning and relabels the LINE step "①LINEで鑑定師に送信(必須)". The LINE button (`#lineSendBtn`, `https://line.me/R/msg/text/?<encoded text>` — the correct deep-link format; an earlier version used the invalid `https://line.me/R/share?text=...`, which just opened the LINE app's home screen instead of the recipient picker) is **always shown, never auto-opened**: opening another native app can only ever happen from an explicit tap in this browser, and a customer choosing a recipient + tapping send inside LINE is not a bug or something this codebase can automate away — a prior version tried auto-firing `window.open()` on submit, which didn't read as "automatic" to users anyway (they still had to pick a recipient and tap send in LINE) and just added a surprise popup, so it was removed in favor of being upfront about which step is required. The **②Stripe payment link** gets `client_reference_id=<name>` appended so the payment can be matched to the submission without asking for the name again. The LINE message body truncates long free-text answers (始めたいこと/希望期間) to keep the share link comfortably short; the full text (including `detail`) is never lost — it's always in the `d=` payload the reading link decodes. The message also closes with a fixed reassurance line ("※このメッセージが送信できていれば、ご依頼は受け付けられています。…") — a customer's own sent messages stay visible in their own LINE chat history, so that line turns the message they can already see into a self-contained confirmation that their request went through, without needing any reply from the account. This exists because an old Netlify-era build of this project *did* auto-reply per-message via a LINE Messaging API webhook running as a Netlify Function — that required a real backend (a Channel Access Token held server-side) and was lost entirely when the site moved to GitHub Pages (which cannot run any server-side code at all); restoring it would mean standing up a new webhook function somewhere and switching the LINE OA's response mode back to "Bot," which is a real architecture change, not a page edit. The completion screen (`#c_done`) is deliberately styled as a receipt for the same reason — a green checkmark, "ご依頼を受け付けました," and a boxed "📋 ご依頼内容の控え" summary the customer sees immediately on this site, before they've even opened LINE, is a confirmation that's guaranteed to render (no bot, no webhook, nothing that can silently fail) and satisfies "let the customer confirm their request went through" without reintroducing a backend.
  - `?mode=reading&d=<encoded>` — practitioner-only view. Decodes the payload, re-runs the same bazi engine plus 大運 (dayun/decade luck cycles), and provides textareas for the practitioner's commentary: ① 四柱推命, ② タロット, ③ 推奨日 第1候補(with a hint to skip boilerplate openers and write definitively — this is paid content), ④ 第2/3候補, ⑤ 動いてはいけない日 (hint explicitly bans wishy-washy phrasing like 「必要であれば」), ⑥ 総合アドバイス (hint requires tying the conclusion to this customer's 日主/命式/timeframe/request specifically, not generic advice). "報告書を生成する" (`buildReport()`) assembles everything into a plain-text report block for copy/paste, using `★`/`●`/`⚠️` markers to visually distinguish the top-pick day from the alternates and the avoid-day (plain text can't carry color), plus bracketed placeholders (`[🖼 ...]`, `[📷 ...]`) marking where the practitioner should attach the amulet image / tarot-spread photo when sending via LINE.
  - `?mode=report&d=<encoded>&c=<encoded>` — **customer-facing, read-only Web版鑑定書**: lets the customer read the full paid report entirely on the web, no PDF download/print required. Added in response to an explicit ask for the web-only experience to feel complete on its own ("プリントアウトせずwebだけ…で完結"). `d` is the same customer-data payload as `?mode=reading`; `c` is a second `enc()`-encoded payload shaped exactly like `collectDraft()`'s output (`{comment_shishu, comment_tarot, comment_date1, ..., comment_addon_0, ...}`). On `?mode=reading`, a new **「📱 お客様がWebだけで読める鑑定書リンク」** panel (`copyReportLink()`) builds this URL from the currently-typed commentary (via `collectDraft()`) plus the page's own `d=`, and copies it (with `withExternalBrowserHint()`, same as the other practitioner-to-LINE links) — the practitioner re-generates and re-sends this link whenever the commentary changes, since it's a snapshot, not a live view. `initCustomerReport(data, commentary)` reuses `initReading(data)` for its side effects (bazi/大運/addon-textarea creation, setting `window._rd`) even though `#modeReading` itself stays hidden, then calls `applyDraft(commentary)` to populate the same hidden `comment_*` textareas `buildReportBlocks()` already reads from — this means the Web report, the PDF, and the practitioner's own preview are all built from the exact same `buildReportBlocks()`/`comment_*` data with zero duplicated rendering logic. Pagination was factored out of `exportPDF()` into two shared functions — `measureAndBucketBlocks(contentBlocks)` (the measure-then-greedily-bucket-into-`PAGE_BUDGET_PX` step) and `buildReportPages(data,bz,c,amuletFile)` (wraps each page's blocks in the same `.pr-frame>.pr-page` watermark/flourish/footer markup `exportPDF()` was already building) — specifically so the Web viewer and the PDF can never visually diverge in what counts as "page 2" vs "page 3": both call `buildReportPages()` and only differ in what they do with the resulting HTML strings (`exportPDF()` `html2canvas`s each into a PDF page; `?mode=report` injects them live into the DOM). The page is presented as a **page-flip book** (`showReportPage()`/`flipTo()`): a `.flip-page-outer` (sized in JS to the current scale factor, `overflow:hidden`) clips a `.flip-page-inner` (the real 794px-wide `.pr-frame`, scaled down via `transform:scale()` computed from the viewport width in `scaleFlipPage()`) so the exact same markup used for the PDF renders responsively on a phone without its own separate mobile stylesheet; turning a page animates the outgoing/incoming page's `rotateY()` + opacity (a lightweight CSS 3D approximation of a page flip, not a canvas/WebGL library — consistent with the no-new-dependency, near-zero-cost constraint). A **🔊 read-aloud button** (`toggleReportSpeak()`) reads the *current page's* visible text via `speechSynthesis` (see the Web Speech API note below) — framed explicitly as an accessibility/convenience selling point, not a replacement for the PDF (the **📥 PDFも保存する** button on this same page just calls the existing `exportPDF()`). No LINE-in-app-browser warning banner is shown here, for the same reason it's already excluded from `?mode=customer`: this mode is read-only HTML + `speechSynthesis` + `exportPDF()`'s own file-download mechanism, none of which depend on `window.print()` or `localStorage`.
  - `?mode=setup` — stores EmailJS credentials (public key, service ID, template ID, notification email) in `localStorage` under `ej_cfg`. **This config is scoped per browser origin** — it does not carry over across domain migrations (e.g. the old Netlify domain to the current GitHub Pages domain) or between devices/browsers, so it silently stops working after any such change until re-entered. This is why EmailJS is treated as a bonus channel, not the primary one.

## Content & product spec

This is the authoritative frame for what the product is supposed to be. Treat future one-line requests as extensions/refinements of this spec, not replacements for it — when a request is ambiguous, default to what's written here rather than re-deriving scope from scratch.

- **Character/assets**: always use the specified 宗玄 portrait (`assets/portrait/sougen.png`) and the five omamori/amulet images (`assets/amulets/{wood,fire,earth,metal,water}.png`, auto-selected by the customer's dominant element). The amulets are generated PNGs (`Pillow`, via a script no longer in the repo) styled as a coin/wax-seal medallion — dark ink disc, gold double ring with dot ornaments, the element's kanji in gold with a soft colored glow, a small romaji caption — using the site's own palette and the Noto Sans CJK font, not photographic/illustrated art. Don't invent new character art or visual identity — extend what's specified; if regenerating the amulets, keep this same medallion style so they stay visually consistent with the portrait and the rest of the site.
- **Free tier (`muryo-soudan.html`)**: a "catch" — birth date (+ gender) only, giving a light personality/tendency read. Deliberately shallow: deep enough that the customer wants to know more, not deep enough to fully satisfy — it exists to drive the CTA into the paid form, not to be a complete reading. **The result screen's CTA card is built to make that gap concrete rather than just asserting it in prose**, using three honest (non-deceptive — nothing here claims a specific real result exists before payment) conversion elements: (1) the CTA heading (`#r_ctaTitle`) is personalized with the customer's own computed 日主/element (`日主「${ST[bz.day.s]}(${dmEl})」のあなたが、動くべき日`, set in `runDiagnosis()`) instead of generic copy, so it reads as "your result," not a template; (2) a `.locked-teaser` box shows the *shape* of what 動くべき日 looks like — three rows labelled 第1候補/第2候補/第3候補 with a 🔒 icon and CSS-`blur()`ed placeholder text (`2026年◯月◯日`, explicitly captioned "(例)" — an example of the shape, never presented as a real computed date) — so the customer sees exactly what they're paying to unlock, not just a description of it; (3) a `.compare-table` lists 無料相談 vs 本鑑定 ¥2,000 row-by-row (命式診断・タロット吉日・動くべき日3日・動いてはいけない日・総合アドバイス・PDF鑑定書) so the added value is scannable, not just narrated in paragraphs. None of this uses fabricated urgency/scarcity (no countdown timers, no fake "N people viewing" counters) or claims about content that doesn't exist yet — the locked-teaser dates are explicitly labelled as an example, not obscured real output.
- **Paid tier — 本鑑定 (`260805.html?mode=customer`, ¥2,000)**: the core deliverable, built on 四柱推命(五行) + タロット as evidence:
  - **動くべき日 ×3** (ranked: 第1候補=最重要, 第2候補, 第3候補), visually distinguished by priority (★ top pick vs ● alternates in the plain-text report; gold-highlighted `.pr-day-top` vs plain `.pr-day` in the PDF). Each day needs both a reason (根拠 — tied to this customer's 命式/日主 and the tarot draw, not generic) and concrete guidance on how to act that day.
  - **動いてはいけない日 ×1**, same treatment (⚠️ marker / red-tinted `.pr-day-avoid`): a reason and explicit guidance on how to spend that day instead. No hedging language ("必要であれば" etc.) — this is paid content and must read as definitive.
  - **総合アドバイス**: ties the recommended/avoid days together into one conclusion specific to this customer's 日主・命式・relationship request・timeframe — not generic advice that could apply to anyone.
- **Upsell — 追加鑑定 (+¥500 each)**: once a customer is satisfied with the 日付 (date) reading, they can add other reading topics (恋愛/相性/勝負運, etc.) using the *same* method (四柱推命+タロット, same evidence-then-guidance structure) at +¥500 per topic. Implemented as: checkboxes on the intake form (`c_addons`) plus an optional short free-text "その他" field (`textarea.short` — deliberately smaller than the main content fields, since it only needs a one-line topic, not a paragraph), carried through the same `enc()`-encoded payload to the reading link; the practitioner's page grows one extra commentary block per requested topic (via `addonLabelsOf(data)`, the single shared helper every addon-rendering spot calls — don't recompute the label list inline, that duplication is exactly what caused drift before); the completion screen's unified payment panel (see below) shows one additional ¥500 button per selected topic. The ¥500 Payment Link is `STRIPE_ADDON_URL` in `260805.html` (the base ¥2,000 one is `STRIPE_BASE_URL`), both real Stripe Payment Links.
- **`thanks.html`** is the "payment complete" landing page set as the *after-payment redirect URL* on both Stripe Payment Links (Stripe dashboard → the Payment Link → "After payment" section → "Don't show confirmation page" / redirect to your website). This is Stripe-side configuration, not something this codebase can set — if a Payment Link's redirect points to a stale/broken URL (e.g. left over from the Netlify domain, which is what originally happened), the customer gets a "Not Found" right after a successful payment, which reads as if the payment or the reading itself failed even though it didn't. `thanks.html` gets no data from Stripe (no `data`/`readingURL` pass-through) — its dynamic part is entirely local: it reads `PENDING_ADDONS_KEY` from `localStorage` (see below) to show any addon payments still outstanding. It is not, and can never be, a personalized result page — the actual reading result is only ever sent manually by the practitioner via LINE, per the `?mode=reading` flow above.
- **Payment buttons deliberately do NOT use `target="_blank"`, and any addon still owed is tracked through `localStorage`, not the tab.** Stripe Payment Links can't combine the base ¥2,000 and variable +¥500 addons into one checkout without a backend, so the customer has to tap through them one at a time — and on mobile (especially in-app browsers), `target="_blank"` does not reliably open a second tab; it was silently replacing the current tab, stranding the customer with no way back to the addon buttons the moment they paid the first one. The fix: payment links navigate normally (no new tab), and `savePendingAddons(name, email, addonLabels)` (called from `renderCompletion()`) writes the still-unpaid addon list (plus the customer's email, see below) to `localStorage[PENDING_ADDONS_KEY]` before any button is shown. Every addon button's click handler calls `removePendingAddon(label)` — treating "tapped the button" as "handled," since there's no backend/webhook to confirm actual payment — so `thanks.html`'s small inline script (which duplicates `STRIPE_ADDON_URL`/`PENDING_ADDONS_KEY` on purpose, matching how the bazi engine is already duplicated across files rather than shared) can read what's left and render continuation buttons after the redirect back from Stripe. The base ¥2,000 is never re-shown there — reaching `thanks.html` at all implies some payment already succeeded.
- **Every separate Stripe Payment Link is its own checkout session, so without help the customer had to type their email address again at every single payment step** (once for the base ¥2,000, once more per +¥500 addon) — reported directly as "毎回メールアドレスを入力させられる." The fix is a single optional `#c_email` field added to "① お客様情報" on the intake form (explicitly labelled "任意・お支払い時の入力を省略できます" — it's a convenience, never required, consistent with this form's other typing-reduction presets). `submitCustomer()` carries `email` through `data` like any other field; `renderCompletion()` appends `&prefilled_email=<email>` (when non-empty) to *every* Stripe link it renders — the base button and each addon button — so Stripe's checkout page shows the email already filled in (still editable, just not re-typed). `savePendingAddons()` now also stores `email` in `localStorage[PENDING_ADDONS_KEY]` alongside `name`/`addonLabels` specifically so `thanks.html`'s own addon-continuation buttons (rendered after redirecting back from the *first* Stripe payment) can append the same `prefilled_email` — otherwise the saving would only cover the first payment and the customer would still be asked again for every addon paid after landing on `thanks.html`.
- **`campaign.html` is a standalone landing page for SNS-driven promotions (built first for a Threads "先着10名様、本鑑定無償" campaign), reusing `intro-landing.html`'s exact visual language (stars background, portrait+rays hero, CSS variables/fonts) rather than inventing a new look.** Its CTA links to `260805.html?mode=customer&campaign=threads10` — the intake form itself is not forked or duplicated; `submitCustomer()` just reads `?campaign=` from the URL (`new URLSearchParams(location.search).get('campaign')`) and carries it through `data.campaign` like any other field, so it round-trips through `enc()`/`dec()` automatically. When `data.campaign` is truthy, `renderCompletion()` (1) excludes the ¥2,000 base amount from the displayed total, (2) replaces the base Stripe button with a `.notice.ok` line reading "🎁 キャンペーン適用により、本鑑定(¥2,000相当)は無償です" instead of a payment link — addon buttons (+¥500 each) still render normally, since the campaign is base-reading-only per its own terms. `initReading()` shows a matching `#r_campaignRow` badge on the practitioner's page so it's obvious at a glance that this customer isn't expected to pay the base amount. **There is deliberately no automatic "N of 10 remaining" counter anywhere** — this app has no backend/database, so no page can know how many other browsers have already submitted; a client-side counter would be fake data presented as real, which conflicts with the site's existing no-fabricated-urgency principle (see the free-tier `.locked-teaser` note above). Enforcing "first 10" is instead the practitioner's own manual process: `campaign.html`'s terms section says slots close "随時" (as they fill) and that closure is announced by hand, both on this page and on SNS — the same honesty-over-automation pattern used throughout this codebase (e.g. `savePendingAddons()`'s "tapped the button = handled" tracking, or the email-delivery-outcome messaging).
- **The LINE-in-app-browser warning banner is intentionally shown only on `?mode=reading`, never on `?mode=customer`.** Both modes used to call `showLineBrowserWarnIfNeeded()` unconditionally, but the underlying problems that banner exists for — `window.print()` not existing in LINE's WebView, and `localStorage` being unreliable there — only ever apply to the *practitioner's* workflow (`exportPDF()`'s canvas/PDF pipeline, and the commentary draft autosave), neither of which the customer-facing intake form uses at all. Showing the same "この端末では正しく動作しない可能性があるのでSafari/Chromeにコピーして開き直してください" warning to a customer who is just filling out a form and paying was a false alarm that added confusing, trust-eroding friction to the one flow that most needs to stay simple (a customer who came from a LINE Official Account chat is *usually* inside LINE's in-app browser, so this banner was showing up constantly for exactly the people it wasn't meant for) — reported as "LINE/Safari/Chromeを依頼者に経由させないでほしい." `#lineWarnCustomer`'s markup and its `showLineBrowserWarnIfNeeded('lineWarnCustomer')` call were removed entirely; `#lineWarnReading` and its call are unchanged, since the practitioner's page genuinely does need it.
- **The completion screen persists itself into the URL, and payment is shown as one combined step, not a sequence.** `submitCustomer()` builds the `data` object, `history.replaceState()`s the URL to `?mode=customer&done=<enc(data)>`, then calls `renderCompletion(data, true)` — the single function (also called on page load when a `done=` param is present, with `false`) that renders the LINE button and an "② お支払い(合計 ¥X,XXX)" panel listing the base ¥2,000 button *and* every addon's ¥500 button together under one heading and one visible total, rather than as separate "②"/"③" steps. This exists because this page's own completion state was previously pure in-memory JS — losing the tab meant losing every payment button with no way back. Encoding it into the URL means any return to that exact link (reload, browser back, re-opening a bookmarked/shared link) restores the identical payment screen. The one thing `renderCompletion` must never do on a `done=`-restored load is re-fire `sendEmailNotify()` — that only happens once, at the real moment of submission (`isFreshSubmit=true`); a restored view shows a neutral "already submitted" notice instead, otherwise every reload would re-notify the practitioner.
- **The practitioner's `?mode=reading` commentary auto-saves as a draft on every keystroke, both to `localStorage` and into the URL itself, and restores from whichever is available.** `initCommentaryDraft(d)` (called right after `initReading(data)`, so it runs after the dynamic per-addon `comment_addon_N` boxes exist) delegates a single `input` listener on `#modeReading` that calls `saveDraft(d)` on any `textarea[id^="comment_"]`. `saveDraft` writes every commentary field to `localStorage[sougen_draft_<d>]` *and* `history.replaceState()`s a `draft=<enc(draft)>` param onto the current URL (same technique as the customer's `done=` param). `loadDraft(d)` prefers a `draft=` URL param if present, falling back to the `localStorage` copy. The `localStorage` half alone only protects against reloading the same reading link *on the same device* — it does nothing if the practitioner writes on a PC and then checks from a phone, since `localStorage` never leaves the browser it was written in, and that mismatch reads exactly like "what I wrote vanished" even though nothing was lost. The URL half fixes that: the practitioner can copy whatever URL is currently in their address bar (it always reflects the latest keystroke) and open it on any other device to see the identical draft, no `localStorage` involved. In practice, relying on the practitioner to notice the address bar silently grew a `draft=` param and copy *that* (instead of reflexively reusing the original short `?mode=reading&d=...` link from LINE, which never gets a `draft=` and will always look "un-filled" again) turned out to be a real source of confusion — so there's also an explicit **「📋 現在の下書き状態のURLをコピー」** button (`copyDraftUrl()`) above the bulk-paste box that copies `location.href` to the clipboard with a confirmation message, so there's an unambiguous, correct action to take instead of manually selecting from the address bar. The reading page also shows a small amulet thumbnail (`#r_workAmulet`, set via the shared `amuletFileFor(c)` helper — also used by `exportPDF()`, so the two never pick different images) directly in the "命式" panel, not just inside the PDF, so the assigned omamori is visible to the practitioner while they're still working, not only in the final export.
- **The actual interpretive writing (④四柱推命・②タロット・day-by-day reasoning・⑥総合アドバイス) is not generated by this codebase — there is no backend, so there is nowhere to safely hold an AI API key, and this app never calls one.** In practice, the practitioner brings the customer's `?mode=reading&d=...` link (or the decoded chart info) to Claude in a chat session, Claude writes the full commentary there, and it comes back for the practitioner to review/edit. To make that paste-back fast, `?mode=reading` has a "✨ 下書きの一括貼り付け" box (`#bulkPasteInput` + `applyBulkPaste()`) above the individual commentary boxes: paste one blob of text using `【四柱推命】` / `【タロット】` / `【推奨日1】<date>` + `【推奨日1理由】` (…2, …3) / `【動いてはいけない日】<date>` + `【動いてはいけない日理由】` / `【総合アドバイス】` / `【追加鑑定:<label>】` markers (`<label>` must exactly match one of the requested addon labels, e.g. `恋愛について`), and `parseBulkPaste()` splits on those `【…】` headings — the text on the *same line* as a marker is treated as a one-line value (used for the date fields), everything until the next marker is the paragraph body — then fans each piece out into its matching textarea and fires a synthetic `input` event on each (so the draft-autosave above picks it up immediately). Individual boxes stay fully editable after a paste; this is a starting point, not a lock-in. When writing this content in a Claude session, always output it in this exact marker format so it can be pasted in one shot instead of manually copied field-by-field. **The single biggest real-world source of "①〜⑥が反映しない/未入力のまま" reports turned out to be pasting the `?mode=reading&d=...` URL itself into `#bulkPasteInput`**, instead of the AI-written commentary text — a URL naturally contains no `【…】` markers, so `parseBulkPaste()` correctly finds nothing, but the old generic "見つかりませんでした" message (a) didn't say *why* (that a URL isn't the right thing to paste there) and (b) auto-hid after a few seconds, so it read as "nothing happened" rather than as an answer. `applyBulkPaste()` now special-cases this: if the trimmed input matches `/^https?:\/\/\S+$/` and contains no `【`, it short-circuits with a message that names the mistake directly and spells out the 3-step fix (copy this page's URL → paste it into an AI chat and ask for the commentary → paste *that reply* here) instead of attempting to parse it. More generally, none of `applyBulkPaste()`'s failure/partial-failure messages auto-hide anymore (`bulkPasteMsg`'s `setTimeout` only fires on a full, nothing-missing success) — the whole reason a "here's what went wrong" message exists is defeated if it can disappear before the practitioner reads it. The box's label and hint text were also rewritten to lead with "(URLではありません)" and spell out the copy-URL → ask-AI → paste-the-reply steps explicitly, rather than assuming that flow was already understood. **A second, distinct real-world "反映しない" case: pasting a genuinely marker-formatted commentary that still failed to populate anything**, traced to an actual customer's (ナッキー3) text using `〖…〗` (white lenticular brackets, U+3016/U+3017) throughout instead of the documented `【…】` (black lenticular brackets, U+3010/U+3011) — visually near-identical but a different Unicode character, so `parseBulkPaste()`'s bracket-matching regex found zero sections. `parseBulkPaste()` now accepts `【〖〔` / `】〗〕` interchangeably as heading delimiters (`〔〕`, tortoise-shell brackets, added for the same reason); `「」` is deliberately excluded since it's used constantly as an ordinary quotation mark within the body text itself and would cause false heading splits. The same real text also exposed two further gaps that `applyBulkPaste()` now handles: (1) when a source doesn't split a day into a separate date-heading and reason-heading — writing e.g. a single `【推奨日1】` heading with no inline date, followed directly by the explanatory paragraph — the old code only ever read `dv.inline` for the date field and had no fallback for the reason field when no matching `理由` heading existed, so that day's entire explanatory paragraph was silently discarded; it now falls back to using that heading's own body text as the reason whenever no separate `理由` heading is found for 推奨日1/2/3 and 動いてはいけない日, so real content is never dropped just because the source skipped mentioning an actual calendar date (a missing date still surfaces downstream as "(未入力)" in `buildReport()`'s preview, so the practitioner still notices and can add one) — the `found`/`missing` tracking (and thus the confirmation message) reflects this so a body-only recovery isn't misreported as fully missing. (2) 追加鑑定 headings matched only the exact documented form `【追加鑑定:<full label>】`; a source that wrote just the bare theme name (e.g. `〖勝負運〗` instead of `【追加鑑定:勝負運について】`) matched nothing, so `applyBulkPaste()` now also accepts a heading that equals or contains the addon label with its trailing "について" stripped. **A third, distinct real-world case: a customer whose 追加鑑定 came from the free-text 「その他」 field (`addonOther`) — where `addonLabelsOf()` uses the customer's own raw, often long, punctuation-heavy question as the "label" itself (e.g. `起業する事業が上手くいくか？法人にした方がよいか？`) — silently and *reliably* failed on every submission that used it**, because the matching logic required a heading to literally contain that entire raw sentence verbatim; no realistic AI-written commentary reproduces a customer's freeform question word-for-word (it naturally gets paraphrased into a short heading), so this addon slot was structurally unmatchable, not just occasionally missed — this is why it looked like it "always fails at the same spot." `applyBulkPaste()`'s addon matching is now two-pass: pass one does the existing label/short-label matching (unchanged, still handles the named `ADDON_LABELS` themes like 恋愛/相性/勝負運); anything that doesn't match in pass one falls through to pass two, which assigns any still-unclaimed `追加鑑定`-prefixed (or bare `その他`) heading to the remaining addon slot(s) *in the order they appear in the pasted text* (tracked in `found` as `…(見出し順で補完)`), so a short paraphrased heading like `【追加鑑定:法人化について】` still lands in the right box even though it doesn't textually match the customer's original question. The on-page hint text (the `③` step instructions above `#bulkPasteInput`) now explicitly tells the practitioner/AI that a paraphrased heading is fine for a 「その他」-sourced addon and doesn't need to repeat the customer's question verbatim.

## Architecture notes

- **The bazi/four-pillars calculation engine is duplicated verbatim in `muryo-soudan.html` and `260805.html`** (solar longitude `sl()`, jieqi solar-term root-finding `flj()`, ganzhi conversion, `bazi()`, `tally()`, five-element weighting, etc.). There is no shared JS module — because there's no build step to share code between static pages, any fix or change to this engine must be applied in both files or they will silently diverge. `260805.html` additionally has the `dayun()` (大運) function that `muryo-soudan.html` doesn't need.
- All customer PII (name, birth date/time, gender, request, timeframe) flows only through the browser: form → base64(JSON) in a URL query param → LINE share text / EmailJS template params. Nothing is persisted server-side; `localStorage` on the practitioner's own device is the only persistence (EmailJS config only), and it does not sync across origins or devices (see the `?mode=setup` note above).
- **Never let automatic delivery fail silently — always show the customer whether it actually worked.** An earlier iteration made EmailJS the sole automatic channel and hid LINE as a small "in case it fails" link with no way to know it had failed; that silently broke the customer-to-practitioner flow entirely (nothing reached the practitioner, with no visible failure on either side) once the EmailJS `localStorage` config stopped applying after the Netlify→GitHub Pages domain change. The fix is not "make LINE the required step forever" — it's that `submitCustomer()` now awaits the EmailJS promise and reflects its real outcome in the UI (see the `?mode=customer` note above), so a silent failure is structurally impossible: the customer is always told plainly whether it's safe to skip LINE or whether LINE is required this time.
- External dependencies are all CDN-loaded, no bundler: Google Fonts (Cinzel, Shippori Mincho B1, Shippori Antique B1, and Yuji Syuku on `intro-landing.html` only) on all three pages, and on `260805.html` only: `@emailjs/browser`, `html2canvas`, and `jspdf` (all jsdelivr CDN).
- Visual language is shared but not code-shared across the three files: dark ink background, gold/lavender palette, "flowing star" canvas-free CSS animation. Each page defines its own copy of these styles.
- `assets/portrait/sougen.png` and `assets/amulets/{wood,fire,earth,metal,water}.png` are referenced by the HTML but treated as optional: every `<img>` for them has `onerror` handling so a missing file degrades gracefully (no broken-image icon) instead of breaking the page. Both exist as of this writing.
- **The practitioner's PDF report (`exportPDF()` in `260805.html`) is deliberately more decorated than the plain-text LINE report (`buildReport()`) can be** — plain text can't carry color or vector graphics, so the PDF is where the "premium, worth paying for" impression has to live. It renders on a bordered ivory page (not plain white) with a gold rule ornament under the title (repeated between every major section, not just once at the top) and four small corner-flourish SVGs (`cornerFlourishSVG(pos)`) framing the page, an inline-SVG 五行 pentagon radar chart (`elementRadarSVG(c)`, sized larger than the on-page version), a distinct SVG icon per section — `baziIconSVG()` (a taiji/陰陽 motif) beside ①四柱推命 and `tarotCardSVG()` beside ②タロット — and the お守り amulet image shown at ~116px inside a circular gold-ring frame (`.pr-amulet-frame`) rather than as a small bare `<img>`. `baziIconSVG()` exists specifically because ①四柱推命 and ②タロット originally both rendered `tarotCardSVG()` — the same icon twice — which read as a bug once the images got bigger and more prominent; the two sections now have visually distinct icons. None of this is photographic/illustrated art — it's CSS + inline SVG, consistent with the no-build-step, no-external-asset architecture — but it reads as considerably more crafted than a bullet list.
- **`exportPDF()` does not use `window.print()` at all — it renders the report to a real PDF file client-side with `html2canvas` + `jsPDF` (both CDN-loaded, `<script>` tags in `<head>`) and downloads it directly.** This replaced an earlier `window.print()`-based approach after repeated "印刷ができません" reports traced back to LINE's own in-app browser (the WebView opened when a link is tapped inside a LINE chat), which does not implement `window.print()` at all — the button was simply a dead click there, and no amount of fixing `exportPDF()`'s own logic (timing, image-load races, etc.) could have helped, because the underlying browser API itself was unavailable. `#printArea` (`.pr-page` inside it) is kept permanently laid out at a fixed 794px width via `position:fixed;left:-9999px` (not `display:none` — html2canvas needs the element actually rendered to capture it) instead of the old `@media print` visibility trick. `exportPDF()` is `async`: it `html2canvas`-captures `.pr-page` into a canvas (`scale:2` for retina sharpness), feeds that image into a new `jsPDF({unit:'mm',format:'a4'})`, paginates across multiple A4 pages if the content is taller than one page (`addImage` in a `heightLeft` loop), and calls `pdf.save(filename)`, which triggers a normal file download — a mechanism that works inside LINE's WebView (and effectively every other browser/webview) because it doesn't depend on the print API at all. The button (`#exportPdfBtn`) is disabled with a "PDFを生成中…" label while this runs, in a `try/finally`, since canvas rendering takes a perceptible moment. **The download filename is deliberately ASCII-only** (`kantei_houkokusho[_<asciiSlugOfName>]_<YYYYMMDD>.pdf`, built via `asciiSlug()` stripping any non-ASCII character) — real-browser testing showed that a `download`-attribute filename containing Japanese characters can silently be discarded (the file saves as a nameless, extension-less "download" instead), which is worse than just omitting the customer's name from the filename since the name is still shown prominently inside the PDF's own content. `initReading()` still warms the お守り image into the browser cache early (via `#r_workAmulet`) so html2canvas doesn't have to wait on a fresh network fetch when it captures the page later.
- **The PDF report's visual design was deliberately overhauled away from a "業務報告書" (business-report) look toward a mystical, certificate/scroll-like one**, per an explicit request to make it feel entertaining and worth the ¥2,000 from the first glance. `.pr-page` is now wrapped in an outer `.pr-frame` (a second gradient-filled border, giving a double-frame look) with a very faint (`opacity:.05`) full-page pentagon watermark (`pageWatermarkSVG()`) sitting behind everything (`.pr-content` wraps the real content at `z-index:1` so it always sits above the watermark). Every text-bearing block — ①四柱推命, ②タロット, each 推奨日/動いてはいけない日 card, 総合アドバイス, and each 追加鑑定 block — is run through `formatParagraphs(text)` instead of a single `<p>` with `<br>`s: it splits on existing blank lines first, then further splits any long block into ~2-sentence paragraphs on `。` boundaries, so a practitioner who just free-types into one textarea (with no manual line breaks) still gets readable, properly-spaced paragraphs in the output rather than one wall of text stretching edge-to-edge. Every major block (①②, each day card, 総合アドバイス, each addon) now carries a small distinct icon in a circular `.pr-icon-badge` — `baziIconSVG()` / `tarotCardSVG()` as before, plus `sunBurstIconSVG()` for the top-priority day, `starIconSVG()` for the other candidate days and each addon, `wardIconSVG()` (a stylized 御札/talisman) for 動いてはいけない日, and `sealIconSVG()` (a red 落款/hanko-style stamp reading 宗玄) both beside 総合アドバイス and again on its own just before the closing line — roughly the "one illustration per box" the design brief asked for. **The 五行 radar chart (`elementRadarSVG(c)`) is now ~2.5× its previous size** (viewBox scaled from 200×210 to 500×524, element kanji from 14px→36px, counts from 9px→20px) and sits under its own labelled subsection (`.pr-evidence-head`, tagged "Evidence · 鑑定の根拠") rather than being a small addendum under the pillars — since the five-element balance is the actual evidence this whole reading is built on, it's treated as one of the report's headline visuals, not a footnote. `exportPDF()`'s `html2canvas()` call now targets `#printArea .pr-frame` (the outer wrapper) rather than `.pr-page` directly, so the outer double-border is included in the captured image. **①四柱推命 and ②タロット each also carry a larger illustrative diagram** (`.pr-illustration`, centered, above the paragraph text) distinct from their small header-badge icon: `baziDiagramSVG()` draws the 五行相生 (generating-cycle) diagram — five colored circular nodes (one per element, using the same `EC` palette as `elementRadarSVG`) arranged in a pentagon and connected by curved arrows in generating order (木→火→土→金→水→木) — rather than a monochrome 陰陽 icon, because a colorful "the elements feed into each other" diagram reads as more inviting/curiosity-inducing than a flat duotone symbol (an explicit design request, with real-world 五行/four-pillars diagrams as reference). `tarotSpreadSVG()` for ② draws three tarot-card shapes with distinct gradient backgrounds and motifs (navy with a moon+stars for 現状, plum with a stylized eye for 課題, amber with a sunburst for 行く先) labelled 現状/課題/行く先 underneath — a generic illustration of "a three-card spread was drawn" with a mystical, colorful card-like look, not a rendering of the specific cards named in the practitioner's free text (which isn't structured data this codebase can parse out of a textarea). `formatParagraphs()` never shortens or drops any of the practitioner's text — it only re-splits it into `<p>` tags; a length check (input string length vs. rendered paragraph text length) confirms an exact match. Any earlier preview that looked shorter was Claude using abbreviated placeholder text to speed up a screenshot check, not evidence of actual truncation — always re-verify against the practitioner's real (full-length) commentary before concluding content is being cut.
- **The mystical redesign above initially made the PDF run to ~10 pages for a realistically long commentary, which reads as bloated rather than premium and is a real burden to scroll/print** — reported directly from a real practitioner-written commentary. The fix was a broad size-down pass across every `.pr-*` rule and every illustration SVG in `260805.html`, not any single change: `.pr-page` padding 20mm/15mm→13mm/11mm; title/eyebrow/name/meta/section-heading font sizes each cut roughly 25-30%; `.pr-section`/`.pr-day` `line-height` cut from ~2.0-2.1 to ~1.5-1.55 and paragraph `margin-bottom` from `.9em`/`.7em` to `.45em`/`.4em` (line-height and paragraph spacing were the single biggest contributors, since they multiply across every sentence in the practitioner's free text); `.pr-section`/`.pr-day` padding and inter-block margins roughly halved; the amulet frame, pillar cards, and every per-section/per-day icon badge (`.pr-icon-badge`, `.pr-day-icon`) shrunk to match. The three illustrative SVGs were scaled down to match: `elementRadarSVG(c)` from viewBox 500×524/470×493px display to 350×366/298×315px (kanji labels 36px→25px), `baziDiagramSVG()` from 230×236/260×266px to 178×183/201×206px (node radius 22→17), `tarotSpreadSVG()` from 360×180px to 255×128px display (viewBox unchanged) — all proportionally, not just shrunk on one axis, so nothing looks stretched. `formatParagraphs()`'s sentence-grouping was also changed from 2 sentences per `<p>` to 3, cutting the number of paragraph breaks (and their margins) by roughly a third without making any single paragraph noticeably harder to read. None of this touches what content appears, only how much room each element of it takes — verified via a Playwright script that runs the real `exportPDF()`/`html2canvas` pipeline and measures the resulting canvas height against A4's 297mm page height: a realistic single-topic reading now renders at 3 pages (was ~10 at the old sizing) and the longest real commentary seen so far (four-pillars + tarot + 3 recommended days + one avoid-day + overall advice + one add-on, all in full paragraph form) renders at 4 pages — comfortably under the "5 pages max" requirement with headroom for future addons.
- **`exportPDF()` was later rewritten to build the report as discrete per-page `.pr-frame` images instead of one continuous canvas sliced by A4 height**, because slicing produced two concrete "doesn't look like a real certificate" complaints: the double-border frame touched the physical paper edge with no margin, and a page break could fall in the middle of a paragraph or card with no border on the pages in between (since only the single, giant source canvas ever had a border drawn around it once). `buildReportBlocks(data,bz,c,amuletFile)` now returns the report as an array of atomic HTML "blocks" (header/命式/五行レーダー, ①四柱推命, ②タロット, each of the 4 day-cards, 総合アドバイス, each addon) plus a separate `closingBlock` — atomic meaning a block is never split across a page boundary. `exportPDF()` first renders all blocks flat into one off-screen `.pr-content` purely to measure each one's real rendered height (`el.offsetTop` deltas, not `offsetHeight` alone, so CSS margin-collapsing between blocks is measured correctly), then greedily buckets them into pages against a `PAGE_BUDGET_PX` (950, chosen empirically — see below) content-height budget, always starting a fresh page rather than exceeding budget except when a single block is already larger than the whole budget (avoids an infinite empty-page loop). Each page bucket is then rebuilt as its own complete `.pr-frame > .pr-page` (watermark, all four corner flourishes, and a new small `.pr-page-footer` reading "五行庵 宗玄 ・ n / N" repeated on every page, reinforcing that this is a proper multi-page document, not an arbitrarily-cut scroll) and `html2canvas`'d individually; `pdf.addImage()` then places each page's image at `x=y=marginMm` (8mm) with `imgWmm = 210-2*marginMm`, giving every page a real, consistent white margin on all four sides instead of full-bleed. `PAGE_BUDGET_PX=950` and `marginMm=8` were tuned together and checked against two things via Playwright: (1) the resulting page count for both a typical single-topic reading and the longest real commentary seen so far (ナッキー3, 8 sections including one addon) — 3-4 pages and 5 pages respectively, still within the "5 pages max" requirement even with the new per-page chrome overhead: 950 was deliberately chosen over a more space-efficient ~1000-1100 to keep meaningful headroom under the physical page-height cap, not to just barely fit; (2) that every page's actual rendered height, converted to mm at the same width-based scale factor used for its 8mm-margin placement, stays safely under the printable area (297mm − 2×8mm = 281mm) — verified up to ~93% utilization on the tallest real page, never clipped. **A `wrap.firstElementChild` bug caught during this rewrite**: reading that property twice (once to `appendChild` it, once as the return value) returned `null` the second time, since `appendChild` had already moved the node out of `wrap` — fixed by capturing the element in a variable once instead.
- **The `②タロット` illustration now shows the practitioner's actual drawn cards when they're written in the documented format, instead of always showing the same fixed generic 現状/課題/行く先 motifs regardless of content.** `detectTarotCards(text)` looks specifically for the pattern the practitioner's own real commentary already uses — `現状は「<カード名>(正位置/逆位置)」です。` / `課題は「...」` / `結果は「...」`(or `行く先は`) — and extracts, for each of the three positions independently, the card name (from a `TAROT_MAJOR` list of the 22 major arcana, or a `<suit>の<rank>` minor-arcana pattern covering all 4 suits under both their katakana and kanji names) plus its orientation. It deliberately anchors to text immediately following each position label (within a short window) rather than matching card names anywhere in the text, because a card mentioned once in an early sentence is often referenced again in the explanatory prose that follows it — matching globally caused false extra matches. `tarotSpreadSVG(detected)` then draws each of the 3 card faces using a suit-appropriate motif (`tarotSuitMotifSVG()`: a flame/torch for ワンド/棒, a chalice for カップ/杯, a blade for ソード/剣, a pentagram-in-circle for ペンタクル/貨幣/コイン, and a celestial moon-and-stars motif shared by all major arcana) with the actual card name printed on the card face and the position + orientation as a small caption underneath — not a full bespoke illustration per card (there are 78), but enough that the card shown genuinely corresponds to what was drawn, rather than being generically decorative. Any position whose card wasn't detected (a practitioner who didn't use this exact phrasing) falls back to the original generic motif for that slot (moon/eye/sun) with just the position label — this is a graceful degradation, never a broken or blank card.
- **Page 1 of the PDF is deliberately reserved as an image-only page**, per an explicit request: `.pr-content` for page 1 holds only the title/name/meta/pillars/amulet header plus the 五行バランス radar chart *and* the ②タロット three-card spread illustration together — all the report's visuals in one place, before any body text. `exportPDF()`'s page-bucketing (`const pages=[[0],[]]`) enforces this structurally: block 0 (the header, which now also contains the tarot-spread illustration) is always alone on page 1, and the greedy budget-fill loop is only ever applied starting from block 1 onward — even if page 1 has leftover room, later text blocks are never pulled forward into it. **The tarot-spread illustration is intentionally rendered twice** — once in the header (page 1) and again inside `tarotBlock` above the ②タロット *text*, wherever that block ends up landing. It was first moved out of `tarotBlock` entirely on the assumption that appearing once on page 1 was enough, but that read as the card illustration having gone missing from its familiar spot next to the ②タロット write-up once bucketing placed that text on a later page — so both copies call `tarotSpreadSVG(detectTarotCards(tarotRaw))` (using the one `tarotRaw`/`detectTarotCards()` result computed once in `buildReportBlocks()`, so the two copies can never disagree about which cards were detected). `.pr-title`'s font-size was also bumped 25px→32px after feedback that it was hard to read on the now-mostly-empty, image-focused page 1 — page 1 isn't part of the shared `PAGE_BUDGET_PX` budget (it's always its own dedicated page regardless of height), so enlarging just this one page's title doesn't affect page count elsewhere; verified via Playwright that the taller title still leaves comfortable headroom under the printable-area cap.
- **A large empty gap on the report's final page (common for a short single-topic reading) is now filled with a decorative closing illustration instead of being left blank**, per an explicit design request that this illustration combine 宗玄氏 (the practitioner) with the customer's dominant element, rather than just reusing the plain amulet PNG. After the page-bucketing step above computes how much of `PAGE_BUDGET_PX` the last page actually used (content blocks + the closing block's estimated height), if the leftover space exceeds 240px, `exportPDF()` inserts a `.pr-closing-illustration` block. `closingAmuletSVG(elIndex, withSeal=true)` draws the underlying medallion — dark disc, gold double ring with dot ornaments (matching the existing amulet PNGs' visual language), the dominant element's kanji large in the center in that element's color, and (when `withSeal` is true) a small red 宗玄 hanko/seal affixed to one edge like a signature; it's used standalone (`withSeal=true`) nowhere currently but kept general. **The actual closing illustration is `closingPortraitOrbHtml(elIndex)`**, added after an explicit request (with a reference image of the character) that the illustration show 宗玄氏 himself gazing at or holding the element, not just an abstract medallion: it reuses the *existing* `assets/portrait/sougen.png` silhouette (the same asset `intro-landing.html`'s hero already uses — no new character art was drawn, per this project's "don't invent new character art" rule) inside a `position:relative` wrapper, with `closingAmuletSVG(elIndex, false)` (seal omitted — the portrait itself now represents 宗玄, so a second signature on the small medallion would be redundant clutter at that size) absolutely positioned at the portrait's upper-right (`.pr-closing-orb`, `top:2%;right:-34%`) — chosen empirically to land where the silhouette's head/gaze naturally points, so the medallion reads as something he's looking toward, not a random floating sticker. Both are captioned "御守 · 五行庵宗玄 × ＜element＞の加護" beneath. `dominantElementIndex(c)` was factored out of `amuletFileFor(c)` (which now calls it) specifically so the header's amulet-file lookup and this closing composition always agree on which element is "dominant," rather than each recomputing `maxI` separately and risking drift. - **LINE's own in-app browser is also the real cause behind repeated "貼り付けたのに未入力" (draft/paste not reflecting) reports** — its storage (`localStorage`) is unreliable, unrelated to any bug in `applyBulkPaste()` or the draft-sync logic, both of which work correctly once the page is actually running in a real browser (Safari/Chrome). This is handled two ways, both unconditional (never an opt-in toggle, per explicit instruction not to make this "partial" or "optional"): (1) `isLineInAppBrowser()` (`/\bLine\//i.test(navigator.userAgent)` — LINE's in-app browser UA reliably includes a `Line/<version>` token) is checked on page load for both `?mode=customer` and `?mode=reading`, and if true, an always-visible `.line-warn` banner (`#lineWarnCustomer` / `#lineWarnReading`, not a toast/dismissible notice) is shown at the very top of the page with a one-tap "このページのURLをコピー" button (`copyCurrentUrlForExternalBrowser()`) so the practitioner can immediately paste into Safari/Chrome instead of guessing what's wrong. (2) Every link this codebase hands to a practitioner *through LINE itself* — the `▼鑑定師用` reading URL in the customer's LINE share message, and the URL `copyDraftUrl()` copies for cross-device continuation — is tagged with `openExternalBrowser=1` (`withExternalBrowserHint(url)`) before being embedded in LINE-bound text; LINE's own client recognizes this query param and opens such links in the device's default browser instead of its in-app WebView when tapped from a chat, so in the common case the broken browser is avoided automatically and the warning banner never needs to appear. `copyTextToClipboard(text, onDone)` is the one shared clipboard helper both `copyDraftUrl()` and `copyCurrentUrlForExternalBrowser()` call, replacing what used to be two near-identical inline copy-to-clipboard implementations.
- **Voice input/output uses only the browser-native Web Speech API** (`SpeechRecognition`/`webkitSpeechRecognition` for dictation, `speechSynthesis`/`SpeechSynthesisUtterance` for read-aloud) — free, no backend, no API key, consistent with this project's near-zero-cost constraint; no third-party speech vendor was introduced. Both are feature-detected once per page (`const SR_CLASS = window.SpeechRecognition || window.webkitSpeechRecognition;` / `'speechSynthesis' in window`) and every mic/speaker button is hidden outright (not disabled) when unsupported, matching the project's existing graceful-degradation rule for optional browser features (LINE's in-app WebView and some Safari/Android builds lack one or both APIs). All recognition calls use `lang='ja-JP'`, `interimResults=false`, `maxAlternatives=1` (final-result-only; no live partial-transcript UI, kept deliberately simple). Implemented independently in `muryo-soudan.html` (`startVoiceNickname()`, `startVoiceDate()`, `toggleSpeak()`) and `260805.html` (`startVoiceDictation()`, `toggleReportSpeak()`/`stopReportSpeak()`) rather than as a shared module, following this codebase's existing duplicate-rather-than-share convention for static pages with no build step (same reasoning as the bazi engine above) — a fix to one must be mirrored in the other if it needs to apply site-wide.
- **PII collected for customer acquisition is deliberately minimal, and this is enforced by what fields exist, not by a privacy policy.** The free-diagnosis funnel (`muryo-soudan.html`) only ever asks for birth date(+optional time) + gender + an optional self-chosen nickname (explicitly captioned "🔒 お名前・ご連絡先は不要です") — no name, email, or phone number anywhere on that page. The paid form (`260805.html?mode=customer`) still requires a name and offers an optional email, but only because Stripe's `client_reference_id`/`prefilled_email` genuinely need something to match a payment back to a request — that's a real constraint of using Stripe Payment Links without a backend (see above), not a data-collection choice independent of it.
- **E-money/digital-wallet payment methods (Apple Pay, Google Pay, konbini, etc.) are a Stripe Dashboard setting on each Payment Link, not something this codebase controls.** `STRIPE_BASE_URL`/`STRIPE_ADDON_URL` are plain Stripe-hosted checkout links; whatever payment methods are toggled on for that Payment Link (Stripe dashboard → Payment Links → the link → Payment methods) are what the customer sees there automatically, with no page-side code change required either way. This codebase's own contribution to "don't make the customer re-enter data" is the existing `prefilled_email` passthrough (see the email-field note above) — it does not and cannot add/remove payment methods itself.
- **Real-world use of the voice features above surfaced four follow-up fixes, all in `muryo-soudan.html`/`260805.html`:**
  1. Browser TTS dictionaries default to reading 「方」 as "ほう", which is wrong whenever it means "person" (「〜を持つ方」, read "かた") — a mispronunciation a real user caught immediately on the free-diagnosis read-aloud. `ELDESC`'s display text is left alone (humans read "方" correctly in context), but `runDiagnosis()` builds `#r_speakText` (the TTS-only plain-text mirror) through a small `spokenEldesc(s)` helper that does `s.replace(/方$/,'かた')` — safe because every `ELDESC` entry is authored to end in exactly that character. This is deliberately **not** applied to `?mode=report`'s read-aloud (`toggleReportSpeak()`), which reads arbitrary practitioner-written free text where 「方」 is genuinely ambiguous (方法/方向/両方/先方 vs. "person") and a blind regex would introduce new mispronunciations as often as it fixes this one.
  2. `muryo-soudan.html`'s optional nickname is now also carried through the `pf=` prefill payload (`runDiagnosis()`'s `prefill` object gains `nickname`) and `260805.html`'s `applyPrefill()` drops it into `#c_name` *only if that field is still empty* — a starting draft the customer can keep or overwrite with their real name, never a silently-forced value. The post-prefill notice text branches on whether a name was actually carried (`nameCarried`) so it never claims to have filled in something it didn't.
  3. The addon "その他" free-text field (`#c_addon_other`) got the same 🎙️`startVoiceDictation()` button as `#c_action`/`#c_detail`, after a direct ask for addon-section voice input — the addon *checkboxes* themselves stay checkbox-only (there's no reliable way to voice-drive a multi-select without a much larger, error-prone intent-parsing layer, which isn't worth it for three checkboxes a thumb can tap directly); the one genuinely free-text field in that section is what actually benefited.
  4. Every 🎙️ voice button (`.voice-dictate-btn` in `260805.html`, `.voice-btn`/`.voice-date-btn` in `muryo-soudan.html`) was restyled from a subtle dashed-gold outline (blending into the page's existing gold palette) to a solid, high-contrast orange (`#ff9142` idle / `#ff6a3d` while listening, dark-ink text) after a direct "the 声で入力 label is hard to notice" report — the goal is an obviously-tappable affordance, not a decorative accent matched to the rest of the UI.
