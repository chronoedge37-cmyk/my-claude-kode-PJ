# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Static site for a LINE Official Account fortune-telling business (五行庵 宗玄 / "五行タロット鑑定" — Five Elements × Tarot readings). No build system, no package manager, no backend/server — three self-contained HTML files, each with inline `<style>` and `<script>`, deployed as-is to **GitHub Pages** (Settings → Pages, "Deploy from branch", `main`, root). The site previously ran on Netlify (one-time "Netlify Drop", never linked to this repo) — that deployment is abandoned; `_redirects` is a leftover Netlify-only file with no effect on GitHub Pages.

There are no build, lint, or test commands — there is no `package.json` and nothing to compile. Verify changes by opening the HTML file directly in a browser (or the deployed GitHub Pages URL) and exercising the relevant flow manually.

`index.html` is a minimal `<meta http-equiv="refresh">` redirect to `intro-landing.html`, needed because GitHub Pages serves whatever is at the repo root and this project's real entry point is `intro-landing.html`.

## Pages and user flow

- `intro-landing.html` — entry page. Hero has a circular portrait slot (`assets/portrait/sougen.png`, a character illustration of 宗玄) ringed by a CSS-only rotating/breathing light-ray effect (`.rays`/`.ray`, generated in the inline `<script>`); if the portrait image is missing, `onerror="this.remove()"` leaves just the empty ring + rays rather than a broken-image icon — there is deliberately no filled placeholder graphic anymore. Links to `muryo-soudan.html`.
- `muryo-soudan.html` — free consultation / self-service diagnosis. Customer enters birth date (+ optional time) and gender; a client-side 四柱推命 (Four Pillars / bazi) engine computes and renders the chart entirely in the browser, including a dominant-element read (`maxI` in `runDiagnosis()`). The result panel shows an amulet image at `assets/amulets/{wood,fire,earth,metal,water}.png` chosen by that dominant element (same graceful `onerror` fallback as the portrait). The CTA button's `href` is built dynamically in `runDiagnosis()`: it points to `260805.html?mode=customer&pf=<encoded birth data>`, base64-encoding the customer's Y/M/D/H/Min/gender so the paid form can prefill them.
- `260805.html` — the paid-reading intake form **and** the practitioner's working page, in one file. Behavior is selected at runtime by a `?mode=` query param, dispatched at the bottom of the `<script>`:
  - `?mode=customer` (default) — customer form: name, birth date/time, gender, **①「始めたいこと」(now a `<textarea>`, encouraged to include background/context, not just a one-line label)**, ②希望期間, and **③「今の状況や気になっていること」(`c_detail`, optional free-text)** added specifically so the practitioner has enough real material to write a personalized ⑥総合アドバイス instead of only the short example-length answers a single-line input invited. `applyPrefill()` reads the `pf` URL param (if present, from the muryo-soudan.html CTA) and pre-fills/selects the birth-date and gender fields so the customer doesn't re-enter them.
    **①「始めたいこと」と②希望期間 are both backed by a `<select>` first, to minimize typing.** `#c_action_preset` (options from the `ACTION_PRESETS` map: 転職・キャリアチェンジ / 起業・独立 / 恋愛・結婚 / 引っ越し・住み替え / 資格取得・受験 / 大きな買い物・契約 / その他) writes a one-line starter sentence into `#c_action` on `change`, but only if the textarea is still empty — it never overwrites something the customer already typed, so it's purely a typing-reduction convenience, not a constraint on what they can say. `#c_period_preset` replaces what used to be a free-text `#c_period` input entirely: its options are `1ヶ月以内` / `3ヶ月以内` / `半年以内` / a computed `<currentYear>年中` / `<currentYear+1>年中` (labelled "今年中"/"来年中" but the *value* is always the literal unambiguous year string, computed fresh from `new Date().getFullYear()` in `initForm()` so it never goes stale) / `特に期限はない` / `日付や年度を指定する(自由入力)` (value `__custom__`, which reveals `#c_period_custom` for anything the presets don't cover). This exists specifically because a free-text answer like "2027年" is genuinely ambiguous — "by 2027" vs "starting in 2027" are both natural readings, and when Claude later writes the actual day recommendations from this data (see below), guessing wrong means picking dates in the wrong year entirely. The preset values are unambiguous by construction, so this ambiguity cannot recur for any future submission; `submitCustomer()` reads `period` as `periodPresetVal==='__custom__' ? c_period_custom.value.trim() : periodPresetVal`. On submit (`submitCustomer()`), the data (including `detail`) is base64-encoded into a URL (`enc()`/`dec()` helpers) that becomes the practitioner's `?mode=reading&d=...` link. `enc()`/`dec()` operate on raw UTF-8 bytes (via `TextEncoder`/`TextDecoder`), not `encodeURIComponent`-then-`btoa` — the latter blows up every Japanese character to ~9 ASCII chars before base64, which was making the LINE share link long enough to risk failing (see below); `dec()` still falls back to the old scheme so already-issued links keep working. Any base64 payload placed into a URL query string (the `d=` and `pf=` params) must be wrapped in `encodeURIComponent()` — base64's own `+`/`/`/`=` characters are otherwise corrupted (`+` in particular gets read back as a space) once `URLSearchParams.get()` parses them out.

    **Delivery is honest about what actually happened, not optimistic.** `submitCustomer()` fires `sendEmailNotify()` (EmailJS) and now *awaits its outcome* to decide what the completion screen tells the customer: on success, `#notifyStatus` shows "✓ 鑑定師のメールに自動で届きました" and the LINE step is relabeled "①LINEでも送る(任意)"; on failure/no-config, it shows a warning and relabels the LINE step "①LINEで鑑定師に送信(必須)". The LINE button (`#lineSendBtn`, `https://line.me/R/msg/text/?<encoded text>` — the correct deep-link format; an earlier version used the invalid `https://line.me/R/share?text=...`, which just opened the LINE app's home screen instead of the recipient picker) is **always shown, never auto-opened**: opening another native app can only ever happen from an explicit tap in this browser, and a customer choosing a recipient + tapping send inside LINE is not a bug or something this codebase can automate away — a prior version tried auto-firing `window.open()` on submit, which didn't read as "automatic" to users anyway (they still had to pick a recipient and tap send in LINE) and just added a surprise popup, so it was removed in favor of being upfront about which step is required. The **②Stripe payment link** gets `client_reference_id=<name>` appended so the payment can be matched to the submission without asking for the name again. The LINE message body truncates long free-text answers (始めたいこと/希望期間) to keep the share link comfortably short; the full text (including `detail`) is never lost — it's always in the `d=` payload the reading link decodes. The message also closes with a fixed reassurance line ("※このメッセージが送信できていれば、ご依頼は受け付けられています。…") — a customer's own sent messages stay visible in their own LINE chat history, so that line turns the message they can already see into a self-contained confirmation that their request went through, without needing any reply from the account. This exists because an old Netlify-era build of this project *did* auto-reply per-message via a LINE Messaging API webhook running as a Netlify Function — that required a real backend (a Channel Access Token held server-side) and was lost entirely when the site moved to GitHub Pages (which cannot run any server-side code at all); restoring it would mean standing up a new webhook function somewhere and switching the LINE OA's response mode back to "Bot," which is a real architecture change, not a page edit. The completion screen (`#c_done`) is deliberately styled as a receipt for the same reason — a green checkmark, "ご依頼を受け付けました," and a boxed "📋 ご依頼内容の控え" summary the customer sees immediately on this site, before they've even opened LINE, is a confirmation that's guaranteed to render (no bot, no webhook, nothing that can silently fail) and satisfies "let the customer confirm their request went through" without reintroducing a backend.
  - `?mode=reading&d=<encoded>` — practitioner-only view. Decodes the payload, re-runs the same bazi engine plus 大運 (dayun/decade luck cycles), and provides textareas for the practitioner's commentary: ① 四柱推命, ② タロット, ③ 推奨日 第1候補(with a hint to skip boilerplate openers and write definitively — this is paid content), ④ 第2/3候補, ⑤ 動いてはいけない日 (hint explicitly bans wishy-washy phrasing like 「必要であれば」), ⑥ 総合アドバイス (hint requires tying the conclusion to this customer's 日主/命式/timeframe/request specifically, not generic advice). "報告書を生成する" (`buildReport()`) assembles everything into a plain-text report block for copy/paste, using `★`/`●`/`⚠️` markers to visually distinguish the top-pick day from the alternates and the avoid-day (plain text can't carry color), plus bracketed placeholders (`[🖼 ...]`, `[📷 ...]`) marking where the practitioner should attach the amulet image / tarot-spread photo when sending via LINE.
  - `?mode=setup` — stores EmailJS credentials (public key, service ID, template ID, notification email) in `localStorage` under `ej_cfg`. **This config is scoped per browser origin** — it does not carry over across domain migrations (e.g. the old Netlify domain to the current GitHub Pages domain) or between devices/browsers, so it silently stops working after any such change until re-entered. This is why EmailJS is treated as a bonus channel, not the primary one.

## Content & product spec

This is the authoritative frame for what the product is supposed to be. Treat future one-line requests as extensions/refinements of this spec, not replacements for it — when a request is ambiguous, default to what's written here rather than re-deriving scope from scratch.

- **Character/assets**: always use the specified 宗玄 portrait (`assets/portrait/sougen.png`) and the five omamori/amulet images (`assets/amulets/{wood,fire,earth,metal,water}.png`, auto-selected by the customer's dominant element). The amulets are generated PNGs (`Pillow`, via a script no longer in the repo) styled as a coin/wax-seal medallion — dark ink disc, gold double ring with dot ornaments, the element's kanji in gold with a soft colored glow, a small romaji caption — using the site's own palette and the Noto Sans CJK font, not photographic/illustrated art. Don't invent new character art or visual identity — extend what's specified; if regenerating the amulets, keep this same medallion style so they stay visually consistent with the portrait and the rest of the site.
- **Free tier (`muryo-soudan.html`)**: a "catch" — birth date (+ gender) only, giving a light personality/tendency read. Deliberately shallow: deep enough that the customer wants to know more, not deep enough to fully satisfy — it exists to drive the CTA into the paid form, not to be a complete reading. **The result screen's CTA card is built to make that gap concrete rather than just asserting it in prose**, using three honest (non-deceptive — nothing here claims a specific real result exists before payment) conversion elements: (1) the CTA heading (`#r_ctaTitle`) is personalized with the customer's own computed 日主/element (`日主「${ST[bz.day.s]}(${dmEl})」のあなたが、動くべき日`, set in `runDiagnosis()`) instead of generic copy, so it reads as "your result," not a template; (2) a `.locked-teaser` box shows the *shape* of what 動くべき日 looks like — three rows labelled 第1候補/第2候補/第3候補 with a 🔒 icon and CSS-`blur()`ed placeholder text (`2026年◯月◯日`, explicitly captioned "(例)" — an example of the shape, never presented as a real computed date) — so the customer sees exactly what they're paying to unlock, not just a description of it; (3) a `.compare-table` lists 無料相談 vs 本鑑定 ¥2,000 row-by-row (命式診断・タロット吉日・動くべき日3日・動いてはいけない日・総合アドバイス・PDF鑑定書) so the added value is scannable, not just narrated in paragraphs. None of this uses fabricated urgency/scarcity (no countdown timers, no fake "N people viewing" counters) or claims about content that doesn't exist yet — the locked-teaser dates are explicitly labelled as an example, not obscured real output.
- **Paid tier — 本鑑定 (`260805.html?mode=customer`, ¥2,000)**: the core deliverable, built on 四柱推命(五行) + タロット as evidence:
  - **動くべき日 ×3** (ranked: 第1候補=最重要, 第2候補, 第3候補), visually distinguished by priority (★ top pick vs ● alternates in the plain-text report; gold-highlighted `.pr-day-top` vs plain `.pr-day` in the PDF). Each day needs both a reason (根拠 — tied to this customer's 命式/日主 and the tarot draw, not generic) and concrete guidance on how to act that day.
  - **動いてはいけない日 ×1**, same treatment (⚠️ marker / red-tinted `.pr-day-avoid`): a reason and explicit guidance on how to spend that day instead. No hedging language ("必要であれば" etc.) — this is paid content and must read as definitive.
  - **総合アドバイス**: ties the recommended/avoid days together into one conclusion specific to this customer's 日主・命式・relationship request・timeframe — not generic advice that could apply to anyone.
- **Upsell — 追加鑑定 (+¥500 each)**: once a customer is satisfied with the 日付 (date) reading, they can add other reading topics (恋愛/相性/勝負運, etc.) using the *same* method (四柱推命+タロット, same evidence-then-guidance structure) at +¥500 per topic. Implemented as: checkboxes on the intake form (`c_addons`) plus an optional short free-text "その他" field (`textarea.short` — deliberately smaller than the main content fields, since it only needs a one-line topic, not a paragraph), carried through the same `enc()`-encoded payload to the reading link; the practitioner's page grows one extra commentary block per requested topic (via `addonLabelsOf(data)`, the single shared helper every addon-rendering spot calls — don't recompute the label list inline, that duplication is exactly what caused drift before); the completion screen's unified payment panel (see below) shows one additional ¥500 button per selected topic. The ¥500 Payment Link is `STRIPE_ADDON_URL` in `260805.html` (the base ¥2,000 one is `STRIPE_BASE_URL`), both real Stripe Payment Links.
- **`thanks.html`** is the "payment complete" landing page set as the *after-payment redirect URL* on both Stripe Payment Links (Stripe dashboard → the Payment Link → "After payment" section → "Don't show confirmation page" / redirect to your website). This is Stripe-side configuration, not something this codebase can set — if a Payment Link's redirect points to a stale/broken URL (e.g. left over from the Netlify domain, which is what originally happened), the customer gets a "Not Found" right after a successful payment, which reads as if the payment or the reading itself failed even though it didn't. `thanks.html` gets no data from Stripe (no `data`/`readingURL` pass-through) — its dynamic part is entirely local: it reads `PENDING_ADDONS_KEY` from `localStorage` (see below) to show any addon payments still outstanding. It is not, and can never be, a personalized result page — the actual reading result is only ever sent manually by the practitioner via LINE, per the `?mode=reading` flow above.
- **Payment buttons deliberately do NOT use `target="_blank"`, and any addon still owed is tracked through `localStorage`, not the tab.** Stripe Payment Links can't combine the base ¥2,000 and variable +¥500 addons into one checkout without a backend, so the customer has to tap through them one at a time — and on mobile (especially in-app browsers), `target="_blank"` does not reliably open a second tab; it was silently replacing the current tab, stranding the customer with no way back to the addon buttons the moment they paid the first one. The fix: payment links navigate normally (no new tab), and `savePendingAddons(name, addonLabels)` (called from `renderCompletion()`) writes the still-unpaid addon list to `localStorage[PENDING_ADDONS_KEY]` before any button is shown. Every addon button's click handler calls `removePendingAddon(label)` — treating "tapped the button" as "handled," since there's no backend/webhook to confirm actual payment — so `thanks.html`'s small inline script (which duplicates `STRIPE_ADDON_URL`/`PENDING_ADDONS_KEY` on purpose, matching how the bazi engine is already duplicated across files rather than shared) can read what's left and render continuation buttons after the redirect back from Stripe. The base ¥2,000 is never re-shown there — reaching `thanks.html` at all implies some payment already succeeded.
- **The completion screen persists itself into the URL, and payment is shown as one combined step, not a sequence.** `submitCustomer()` builds the `data` object, `history.replaceState()`s the URL to `?mode=customer&done=<enc(data)>`, then calls `renderCompletion(data, true)` — the single function (also called on page load when a `done=` param is present, with `false`) that renders the LINE button and an "② お支払い(合計 ¥X,XXX)" panel listing the base ¥2,000 button *and* every addon's ¥500 button together under one heading and one visible total, rather than as separate "②"/"③" steps. This exists because this page's own completion state was previously pure in-memory JS — losing the tab meant losing every payment button with no way back. Encoding it into the URL means any return to that exact link (reload, browser back, re-opening a bookmarked/shared link) restores the identical payment screen. The one thing `renderCompletion` must never do on a `done=`-restored load is re-fire `sendEmailNotify()` — that only happens once, at the real moment of submission (`isFreshSubmit=true`); a restored view shows a neutral "already submitted" notice instead, otherwise every reload would re-notify the practitioner.
- **The practitioner's `?mode=reading` commentary auto-saves as a draft on every keystroke, both to `localStorage` and into the URL itself, and restores from whichever is available.** `initCommentaryDraft(d)` (called right after `initReading(data)`, so it runs after the dynamic per-addon `comment_addon_N` boxes exist) delegates a single `input` listener on `#modeReading` that calls `saveDraft(d)` on any `textarea[id^="comment_"]`. `saveDraft` writes every commentary field to `localStorage[sougen_draft_<d>]` *and* `history.replaceState()`s a `draft=<enc(draft)>` param onto the current URL (same technique as the customer's `done=` param). `loadDraft(d)` prefers a `draft=` URL param if present, falling back to the `localStorage` copy. The `localStorage` half alone only protects against reloading the same reading link *on the same device* — it does nothing if the practitioner writes on a PC and then checks from a phone, since `localStorage` never leaves the browser it was written in, and that mismatch reads exactly like "what I wrote vanished" even though nothing was lost. The URL half fixes that: the practitioner can copy whatever URL is currently in their address bar (it always reflects the latest keystroke) and open it on any other device to see the identical draft, no `localStorage` involved. In practice, relying on the practitioner to notice the address bar silently grew a `draft=` param and copy *that* (instead of reflexively reusing the original short `?mode=reading&d=...` link from LINE, which never gets a `draft=` and will always look "un-filled" again) turned out to be a real source of confusion — so there's also an explicit **「📋 現在の下書き状態のURLをコピー」** button (`copyDraftUrl()`) above the bulk-paste box that copies `location.href` to the clipboard with a confirmation message, so there's an unambiguous, correct action to take instead of manually selecting from the address bar. The reading page also shows a small amulet thumbnail (`#r_workAmulet`, set via the shared `amuletFileFor(c)` helper — also used by `exportPDF()`, so the two never pick different images) directly in the "命式" panel, not just inside the PDF, so the assigned omamori is visible to the practitioner while they're still working, not only in the final export.
- **The actual interpretive writing (④四柱推命・②タロット・day-by-day reasoning・⑥総合アドバイス) is not generated by this codebase — there is no backend, so there is nowhere to safely hold an AI API key, and this app never calls one.** In practice, the practitioner brings the customer's `?mode=reading&d=...` link (or the decoded chart info) to Claude in a chat session, Claude writes the full commentary there, and it comes back for the practitioner to review/edit. To make that paste-back fast, `?mode=reading` has a "✨ 下書きの一括貼り付け" box (`#bulkPasteInput` + `applyBulkPaste()`) above the individual commentary boxes: paste one blob of text using `【四柱推命】` / `【タロット】` / `【推奨日1】<date>` + `【推奨日1理由】` (…2, …3) / `【動いてはいけない日】<date>` + `【動いてはいけない日理由】` / `【総合アドバイス】` / `【追加鑑定:<label>】` markers (`<label>` must exactly match one of the requested addon labels, e.g. `恋愛について`), and `parseBulkPaste()` splits on those `【…】` headings — the text on the *same line* as a marker is treated as a one-line value (used for the date fields), everything until the next marker is the paragraph body — then fans each piece out into its matching textarea and fires a synthetic `input` event on each (so the draft-autosave above picks it up immediately). Individual boxes stay fully editable after a paste; this is a starting point, not a lock-in. When writing this content in a Claude session, always output it in this exact marker format so it can be pasted in one shot instead of manually copied field-by-field. **The single biggest real-world source of "①〜⑥が反映しない/未入力のまま" reports turned out to be pasting the `?mode=reading&d=...` URL itself into `#bulkPasteInput`**, instead of the AI-written commentary text — a URL naturally contains no `【…】` markers, so `parseBulkPaste()` correctly finds nothing, but the old generic "見つかりませんでした" message (a) didn't say *why* (that a URL isn't the right thing to paste there) and (b) auto-hid after a few seconds, so it read as "nothing happened" rather than as an answer. `applyBulkPaste()` now special-cases this: if the trimmed input matches `/^https?:\/\/\S+$/` and contains no `【`, it short-circuits with a message that names the mistake directly and spells out the 3-step fix (copy this page's URL → paste it into an AI chat and ask for the commentary → paste *that reply* here) instead of attempting to parse it. More generally, none of `applyBulkPaste()`'s failure/partial-failure messages auto-hide anymore (`bulkPasteMsg`'s `setTimeout` only fires on a full, nothing-missing success) — the whole reason a "here's what went wrong" message exists is defeated if it can disappear before the practitioner reads it. The box's label and hint text were also rewritten to lead with "(URLではありません)" and spell out the copy-URL → ask-AI → paste-the-reply steps explicitly, rather than assuming that flow was already understood. **A second, distinct real-world "反映しない" case: pasting a genuinely marker-formatted commentary that still failed to populate anything**, traced to an actual customer's (ナッキー3) text using `〖…〗` (white lenticular brackets, U+3016/U+3017) throughout instead of the documented `【…】` (black lenticular brackets, U+3010/U+3011) — visually near-identical but a different Unicode character, so `parseBulkPaste()`'s bracket-matching regex found zero sections. `parseBulkPaste()` now accepts `【〖〔` / `】〗〕` interchangeably as heading delimiters (`〔〕`, tortoise-shell brackets, added for the same reason); `「」` is deliberately excluded since it's used constantly as an ordinary quotation mark within the body text itself and would cause false heading splits. The same real text also exposed two further gaps that `applyBulkPaste()` now handles: (1) when a source doesn't split a day into a separate date-heading and reason-heading — writing e.g. a single `【推奨日1】` heading with no inline date, followed directly by the explanatory paragraph — the old code only ever read `dv.inline` for the date field and had no fallback for the reason field when no matching `理由` heading existed, so that day's entire explanatory paragraph was silently discarded; it now falls back to using that heading's own body text as the reason whenever no separate `理由` heading is found for 推奨日1/2/3 and 動いてはいけない日, so real content is never dropped just because the source skipped mentioning an actual calendar date (a missing date still surfaces downstream as "(未入力)" in `buildReport()`'s preview, so the practitioner still notices and can add one) — the `found`/`missing` tracking (and thus the confirmation message) reflects this so a body-only recovery isn't misreported as fully missing. (2) 追加鑑定 headings matched only the exact documented form `【追加鑑定:<full label>】`; a source that wrote just the bare theme name (e.g. `〖勝負運〗` instead of `【追加鑑定:勝負運について】`) matched nothing, so `applyBulkPaste()` now also accepts a heading that equals or contains the addon label with its trailing "について" stripped.

## Architecture notes

- **The bazi/four-pillars calculation engine is duplicated verbatim in `muryo-soudan.html` and `260805.html`** (solar longitude `sl()`, jieqi solar-term root-finding `flj()`, ganzhi conversion, `bazi()`, `tally()`, five-element weighting, etc.). There is no shared JS module — because there's no build step to share code between static pages, any fix or change to this engine must be applied in both files or they will silently diverge. `260805.html` additionally has the `dayun()` (大運) function that `muryo-soudan.html` doesn't need.
- All customer PII (name, birth date/time, gender, request, timeframe) flows only through the browser: form → base64(JSON) in a URL query param → LINE share text / EmailJS template params. Nothing is persisted server-side; `localStorage` on the practitioner's own device is the only persistence (EmailJS config only), and it does not sync across origins or devices (see the `?mode=setup` note above).
- **Never let automatic delivery fail silently — always show the customer whether it actually worked.** An earlier iteration made EmailJS the sole automatic channel and hid LINE as a small "in case it fails" link with no way to know it had failed; that silently broke the customer-to-practitioner flow entirely (nothing reached the practitioner, with no visible failure on either side) once the EmailJS `localStorage` config stopped applying after the Netlify→GitHub Pages domain change. The fix is not "make LINE the required step forever" — it's that `submitCustomer()` now awaits the EmailJS promise and reflects its real outcome in the UI (see the `?mode=customer` note above), so a silent failure is structurally impossible: the customer is always told plainly whether it's safe to skip LINE or whether LINE is required this time.
- External dependencies are all CDN-loaded, no bundler: Google Fonts (Cinzel, Shippori Mincho B1, Shippori Antique B1, and Yuji Syuku on `intro-landing.html` only) on all three pages, and on `260805.html` only: `@emailjs/browser`, `html2canvas`, and `jspdf` (all jsdelivr CDN).
- Visual language is shared but not code-shared across the three files: dark ink background, gold/lavender palette, "flowing star" canvas-free CSS animation. Each page defines its own copy of these styles.
- `assets/portrait/sougen.png` and `assets/amulets/{wood,fire,earth,metal,water}.png` are referenced by the HTML but treated as optional: every `<img>` for them has `onerror` handling so a missing file degrades gracefully (no broken-image icon) instead of breaking the page. Both exist as of this writing.
- **The practitioner's PDF report (`exportPDF()` in `260805.html`) is deliberately more decorated than the plain-text LINE report (`buildReport()`) can be** — plain text can't carry color or vector graphics, so the PDF is where the "premium, worth paying for" impression has to live. It renders on a bordered ivory page (not plain white) with a gold rule ornament under the title (repeated between every major section, not just once at the top) and four small corner-flourish SVGs (`cornerFlourishSVG(pos)`) framing the page, an inline-SVG 五行 pentagon radar chart (`elementRadarSVG(c)`, sized larger than the on-page version), a distinct SVG icon per section — `baziIconSVG()` (a taiji/陰陽 motif) beside ①四柱推命 and `tarotCardSVG()` beside ②タロット — and the お守り amulet image shown at ~116px inside a circular gold-ring frame (`.pr-amulet-frame`) rather than as a small bare `<img>`. `baziIconSVG()` exists specifically because ①四柱推命 and ②タロット originally both rendered `tarotCardSVG()` — the same icon twice — which read as a bug once the images got bigger and more prominent; the two sections now have visually distinct icons. None of this is photographic/illustrated art — it's CSS + inline SVG, consistent with the no-build-step, no-external-asset architecture — but it reads as considerably more crafted than a bullet list.
- **`exportPDF()` does not use `window.print()` at all — it renders the report to a real PDF file client-side with `html2canvas` + `jsPDF` (both CDN-loaded, `<script>` tags in `<head>`) and downloads it directly.** This replaced an earlier `window.print()`-based approach after repeated "印刷ができません" reports traced back to LINE's own in-app browser (the WebView opened when a link is tapped inside a LINE chat), which does not implement `window.print()` at all — the button was simply a dead click there, and no amount of fixing `exportPDF()`'s own logic (timing, image-load races, etc.) could have helped, because the underlying browser API itself was unavailable. `#printArea` (`.pr-page` inside it) is kept permanently laid out at a fixed 794px width via `position:fixed;left:-9999px` (not `display:none` — html2canvas needs the element actually rendered to capture it) instead of the old `@media print` visibility trick. `exportPDF()` is `async`: it `html2canvas`-captures `.pr-page` into a canvas (`scale:2` for retina sharpness), feeds that image into a new `jsPDF({unit:'mm',format:'a4'})`, paginates across multiple A4 pages if the content is taller than one page (`addImage` in a `heightLeft` loop), and calls `pdf.save(filename)`, which triggers a normal file download — a mechanism that works inside LINE's WebView (and effectively every other browser/webview) because it doesn't depend on the print API at all. The button (`#exportPdfBtn`) is disabled with a "PDFを生成中…" label while this runs, in a `try/finally`, since canvas rendering takes a perceptible moment. **The download filename is deliberately ASCII-only** (`kantei_houkokusho[_<asciiSlugOfName>]_<YYYYMMDD>.pdf`, built via `asciiSlug()` stripping any non-ASCII character) — real-browser testing showed that a `download`-attribute filename containing Japanese characters can silently be discarded (the file saves as a nameless, extension-less "download" instead), which is worse than just omitting the customer's name from the filename since the name is still shown prominently inside the PDF's own content. `initReading()` still warms the お守り image into the browser cache early (via `#r_workAmulet`) so html2canvas doesn't have to wait on a fresh network fetch when it captures the page later.
- **The PDF report's visual design was deliberately overhauled away from a "業務報告書" (business-report) look toward a mystical, certificate/scroll-like one**, per an explicit request to make it feel entertaining and worth the ¥2,000 from the first glance. `.pr-page` is now wrapped in an outer `.pr-frame` (a second gradient-filled border, giving a double-frame look) with a very faint (`opacity:.05`) full-page pentagon watermark (`pageWatermarkSVG()`) sitting behind everything (`.pr-content` wraps the real content at `z-index:1` so it always sits above the watermark). Every text-bearing block — ①四柱推命, ②タロット, each 推奨日/動いてはいけない日 card, 総合アドバイス, and each 追加鑑定 block — is run through `formatParagraphs(text)` instead of a single `<p>` with `<br>`s: it splits on existing blank lines first, then further splits any long block into ~2-sentence paragraphs on `。` boundaries, so a practitioner who just free-types into one textarea (with no manual line breaks) still gets readable, properly-spaced paragraphs in the output rather than one wall of text stretching edge-to-edge. Every major block (①②, each day card, 総合アドバイス, each addon) now carries a small distinct icon in a circular `.pr-icon-badge` — `baziIconSVG()` / `tarotCardSVG()` as before, plus `sunBurstIconSVG()` for the top-priority day, `starIconSVG()` for the other candidate days and each addon, `wardIconSVG()` (a stylized 御札/talisman) for 動いてはいけない日, and `sealIconSVG()` (a red 落款/hanko-style stamp reading 宗玄) both beside 総合アドバイス and again on its own just before the closing line — roughly the "one illustration per box" the design brief asked for. **The 五行 radar chart (`elementRadarSVG(c)`) is now ~2.5× its previous size** (viewBox scaled from 200×210 to 500×524, element kanji from 14px→36px, counts from 9px→20px) and sits under its own labelled subsection (`.pr-evidence-head`, tagged "Evidence · 鑑定の根拠") rather than being a small addendum under the pillars — since the five-element balance is the actual evidence this whole reading is built on, it's treated as one of the report's headline visuals, not a footnote. `exportPDF()`'s `html2canvas()` call now targets `#printArea .pr-frame` (the outer wrapper) rather than `.pr-page` directly, so the outer double-border is included in the captured image. **①四柱推命 and ②タロット each also carry a larger illustrative diagram** (`.pr-illustration`, centered, above the paragraph text) distinct from their small header-badge icon: `baziDiagramSVG()` draws the 五行相生 (generating-cycle) diagram — five colored circular nodes (one per element, using the same `EC` palette as `elementRadarSVG`) arranged in a pentagon and connected by curved arrows in generating order (木→火→土→金→水→木) — rather than a monochrome 陰陽 icon, because a colorful "the elements feed into each other" diagram reads as more inviting/curiosity-inducing than a flat duotone symbol (an explicit design request, with real-world 五行/four-pillars diagrams as reference). `tarotSpreadSVG()` for ② draws three tarot-card shapes with distinct gradient backgrounds and motifs (navy with a moon+stars for 現状, plum with a stylized eye for 課題, amber with a sunburst for 行く先) labelled 現状/課題/行く先 underneath — a generic illustration of "a three-card spread was drawn" with a mystical, colorful card-like look, not a rendering of the specific cards named in the practitioner's free text (which isn't structured data this codebase can parse out of a textarea). `formatParagraphs()` never shortens or drops any of the practitioner's text — it only re-splits it into `<p>` tags; a length check (input string length vs. rendered paragraph text length) confirms an exact match. Any earlier preview that looked shorter was Claude using abbreviated placeholder text to speed up a screenshot check, not evidence of actual truncation — always re-verify against the practitioner's real (full-length) commentary before concluding content is being cut.
- **LINE's own in-app browser is also the real cause behind repeated "貼り付けたのに未入力" (draft/paste not reflecting) reports** — its storage (`localStorage`) is unreliable, unrelated to any bug in `applyBulkPaste()` or the draft-sync logic, both of which work correctly once the page is actually running in a real browser (Safari/Chrome). This is handled two ways, both unconditional (never an opt-in toggle, per explicit instruction not to make this "partial" or "optional"): (1) `isLineInAppBrowser()` (`/\bLine\//i.test(navigator.userAgent)` — LINE's in-app browser UA reliably includes a `Line/<version>` token) is checked on page load for both `?mode=customer` and `?mode=reading`, and if true, an always-visible `.line-warn` banner (`#lineWarnCustomer` / `#lineWarnReading`, not a toast/dismissible notice) is shown at the very top of the page with a one-tap "このページのURLをコピー" button (`copyCurrentUrlForExternalBrowser()`) so the practitioner can immediately paste into Safari/Chrome instead of guessing what's wrong. (2) Every link this codebase hands to a practitioner *through LINE itself* — the `▼鑑定師用` reading URL in the customer's LINE share message, and the URL `copyDraftUrl()` copies for cross-device continuation — is tagged with `openExternalBrowser=1` (`withExternalBrowserHint(url)`) before being embedded in LINE-bound text; LINE's own client recognizes this query param and opens such links in the device's default browser instead of its in-app WebView when tapped from a chat, so in the common case the broken browser is avoided automatically and the warning banner never needs to appear. `copyTextToClipboard(text, onDone)` is the one shared clipboard helper both `copyDraftUrl()` and `copyCurrentUrlForExternalBrowser()` call, replacing what used to be two near-identical inline copy-to-clipboard implementations.
